# Engine — 思考の熱機関としての M3E

最終更新: 2026-11-18

M3E の「Engine」は、思考の構造を動かす仕組みという意味と、**熱機関**という意味の両方を持つ。この文書は、熱機関としての見方を M3E の思想として定める。

## 1. 中心の命題

**M3E は、温度の差を保ったまま「加熱 → 膨張 → 冷却 → 圧縮」を循環させ、構造の変化を仕事として取り出す、思考の熱機関である。**

熱機関は、温度を上げるだけでも下げるだけでも仕事をしない。高温側と低温側の差を保ち、その間を循環して初めて仕事が出る。思考の道具には、どちらか一方に寄ったものが多い。

| 寄り方 | 例 | 得意 | 欠けるもの |
|---|---|---|---|
| 加熱に寄る | 生成 AI、ブレインストーミングの道具、無限キャンバス | 分岐を増やし、案を出す | 評価と収束 |
| 冷却に寄る | ノート整理、タスク管理、厳密な階層 | 整合と収束 | 初期の形から大きく外れること |

M3E は、この両方を一つの map の上で循環させる。

## 2. 循環の 4 段階

| 段階 | 起きること | 担い手の典型 | 帯域との対応 |
|---|---|---|---|
| 加熱 | 制約と評価を緩め、曖昧さを許す | AI agent の生成 | 探索（Flash の側） |
| 膨張 | node と分岐が増え、自由度が上がる | 案の列挙、別案の並列 | 探索（Flash の側） |
| 冷却 | 評価を強め、選ぶ | human の選別、不整合の排除 | 収束（Deep の側） |
| 圧縮 | 統合し、冗長を除き、階層を整える | 統合、整理、scope の組み直し | 収束（Deep の側） |

- 圧縮では情報が失われる。履歴は journal に残るが、構造は元に戻らない。そのため、同じ循環を回しても毎回違う構造に着く。
- 「AI は提案し、human が確定する」（[Principle.md](./Principle.md) 5）は、この循環では「AI agent が加熱し、human が冷却する」という分担として現れる。分担は典型であって固定ではない。

## 3. 状態の量

| 量 | 意味 | 求め方の方針 |
|---|---|---|
| 温度 | **曖昧さ**。どの選択肢に落ち着くかが定まっていない度合い | 構造から観測する。エントロピーで定義し、0〜1 に正規化する |
| 体積 | 自由度。scope の面に載る node の数 | 構造から数える |
| 膨張・圧縮の速さ | 面の上で node が増える速さと減る速さ | 確定の履歴から、時間で減る累積として数える |
| 活動 | どれだけ頻繁に変更されているか | 確定の履歴から数える。**温度とは呼ばない** |
| エネルギー | 不整合・冗長・未整理の度合い | 未定義。何を不整合とするかの評価基準が要る |
| 仕事 | 構造の変化。新しい構造、より整った配置、以前は届かなかった構造 | 量としては測らない |

- 温度を「活動の多さ」と読む案もあった。M3E では温度を曖昧さに使い、活動は別の量として持つ。よく変更される箇所が曖昧とは限らないからである。
- 温度の差の単位は scope である。scope は map の対象を一枚の面で切り出したもの（[Glossary](../00_Home/Glossary.md)）なので、温度は「面ごとの温度」として定まる。温度の高い面と低い面の差が、熱機関の高温側と低温側にあたる。

## 4. LLM の温度との関係

LLM の温度は、出力の候補を \(p_i \propto e^{z_i/T}\) で選ぶときの \(T\) である。\(T\) が高いほど出力分布のエントロピーが上がり、選択が定まらなくなる。map の温度を曖昧さ（エントロピー）で定義すると、両者は同じ構造の量になる。

- **向きが違う**: LLM の温度は生成の前に設定する**制御量**、map の温度は構造から測る**観測量**である。
- **map → LLM**: 温度の高い面で作業する AI agent は LLM の温度を上げて発散的に生成し、低い面では下げて正確に整理する。これが循環を回す操作になる。
- **LLM → map**: 高い温度で生成された node は、その面の温度を上げる。
- map の温度から LLM の温度への写し方は、agent を動かすときの設定であり、map のデータには入れない。適した範囲が model ごとに違うので、map を特定の model に縛らないためである。

## 5. 量の持ち方の原則

1. **量は正本に入れない**: 温度・体積・活動などは、正本（journal と record）から作り直せる観測量として持つ。正本に入れると、構造と値が食い違ったときにどちらが正しいか決まらない。
2. **確定のときに計算してキャッシュする**: agent が問い合わせるたびに計算させない。agent は値を読むだけで、計算を待つ必要も、計算方法を知る必要もない。キャッシュはサーバの手元に置き、Neo4j と portable snapshot にはその写しを置く。
3. **時間で減る量も、読むときは掛け算 1 回にする**: 保存するのは、最後に確定したときの値と時刻だけにする。
4. **重みの要らない定義を先に採る**: 重みを先に決めると根拠のない値になり、agent が読み始めた後で式を変えると意味がずれる。複数の量を合成する式は、実データの分布を見てから決める。
5. **量の意味は MCP のリソースに一度だけ書く**: agent ごとに教え込まない。

## 6. 決まっていないこと

保存の形に関わる点は、record schema の設計で決める。

- 極性（支持・反対・中立・両面）を親子 edge と GraphLink に付けるか、node に付けるか
- 極性の値の範囲
- 温度の具体的な式。子の極性の分布の正規化エントロピーを第一案とする。極性で測れない曖昧さ（選択肢が並んだまま、まだ選ばれていない状態）をどう印すか
- 活動の累積値を portable snapshot に残すか
- エネルギーの評価基準
