# 外部からのスコープ追加中に画面更新レートが低下した観察

Basis: TOB-O

2026-10-21。利用者からの報告と、同時に実行していた追加処理の状況を残す。原因調査・再現測定・性能修正は未実施。

## 利用者が観察したこと

数学概念のスコープを追加している途中、画面更新は約20Hzだった。スコープ外へ移動すると重さをそこまで感じず、約60Hzで動いた。

利用者の問いは「ノードを追加する外部操作が行われているとき、画面更新レートが低下するのか」。外部追加との時間的な一致と、表示場所による差がある点を調査対象とする。約20Hz・約60Hzは利用者の観察値であり、このメモを作成したエージェントの測定値ではない。

測定方法、対象の操作（パン・ズーム等）、利用者側の実際の描画経路、低下時に開いていた正確なスコープは未記録。「スコープ外」が同一マップ内の別スコープか、別マップかも未確定。勝手に補完しない。

## 同時に実行していた処理

| 項目 | 状況 |
|---|---|
| 配置先 | `M:(研究)> notions` |
| 入力 | 数学概念の独立したMermaid図646件 |
| 操作 | 各図の根を一つのスコープにして、指定親の末尾へ順次追加 |
| 実行経路 | スクリプト → 既存M3E SDK → `m3e_create(kind=import_structure)` → 既存Core・保存・通知 |
| 並列性 | 実際の投入は逐次。子エージェントによる同時書き込みではない |
| 保存完了の時間帯 | 2026-10-21 09:53:00〜10:07:47、日本時間。最初・最後の保存応答の記録による |
| 追加量 | 646スコープ、内部を含め16,399ノード、親子辺のラベル15,753本 |
| マップ全体 | 追加前3,751ノード → 追加後20,150ノード |
| 保存単位 | 一つの概念図につき一回の原子的な追加。各ノードを個別保存したのではない |
| 保存応答の間隔 | 中央値約1.36秒、最小約0.24秒、最大約4.99秒。投入記録から計算 |
| 稼働版 | 辺ラベルを既存属性として引き継ぐ取り込み修正を反映した通常Beta |

「約20Hz」は画面側の観察であり、外部書き込みが毎秒20回あったという意味ではない。通知の実際の到着間隔・再取得回数は採取していない。

追加後の読み戻しでは、全ノード本文・辺ラベル・親子関係・兄弟順序・元のMermaid・出典コメントが一致し、既存ノードとスコープ付属データも保持されていた。このデータ検証や、代表図のヘッドレス表示確認は、利用者の操作中の60Hzを検証したものではない。

## コードで確認できる処理経路

[Viewerの `initDocWatch()` / `applyExternalUpdate()`](../../beta/src/browser/viewer.ts) は、同じマップの `map_updated` 通知を受けると、次の処理を行う。自分自身の保存・重複通知・未保存編集中等の除外条件はある。

通知の受信 → マップ全体の再取得 → JSONの解釈と文書形状の正規化 → 保存比較用状態の複製 → 表示状態の復元 → `render()` → 別タブへの状態通知。

`applyExternalUpdate()` の `render()` は引数を渡していないため、既定の非増分経路に入る。`renderScene()` ではレイアウト・ノード・辺のキャッシュ更新や `treeSpanCache` の消去、`buildLayout()` の呼び出しがある。[サーバー側の `broadcastMapUpdate()`](../../beta/src/node/start_viewer.ts) は、保存したマップを購読する画面へ更新を通知する。

外部更新の受信からこの処理へ入ることはコード上で確認した。各段階の時間、処理の重なり、フレーム落ちとの因果関係は測定していない。

## 現時点の仮説

外部追加のたびに行う全体再取得・状態複製・非増分描画が、同時に行うパン等と処理時間を取り合う可能性がある。マップの成長による全体処理の増加と、表示中スコープのレイアウト・シーン更新の負荷を分けて調べる必要がある。

スコープ外で約60Hzだったという差は重要。同一マップの別スコープであれば、マップ単位の通知や全体再取得だけでは差を説明しきれず、表示範囲の処理が候補となる。別マップであれば、購読しているマップへの通知の有無自体が異なる。どちらだったかは未確認。

「外部操作があると常に20Hzになる」「ノード数だけが原因」「WebGLだけの問題」とは結論しない。

## 次の調査

まず当時の表示スコープ・操作・更新レートの測り方を特定する。その後、同じ保存状態・同じ操作・同じ描画経路を用い、外部追加の有無と表示場所を切り分ける。

| 比較 | 確認したいこと |
|---|---|
| 外部追加なし / あり | ノード総数の差ではなく、追加・通知の処理中に悪化するか |
| 追加対象のスコープ内 / 同一マップの別スコープ | 全体処理と表示範囲の処理を切り分ける |
| 同一マップ / 別マップ | マップ単位の通知・再取得の影響を切り分ける |

通知の到着、再取得・JSON解釈・状態複製・レイアウト・シーン更新の時間、長いタスク、操作中のフレーム間隔を同じ時系列で採取する。外部追加を伴う比較は一時データで行い、利用者の研究マップを測定用に再編集しない。

[更新情報の計測実装](../../beta/src/rendering/render_update_metrics.ts) の呼出頻度・CPU側経過時間と、実際に画面へ提示されるフレームレートは区別する。Inspectorの更新回数だけで60Hzの操作感を達成したと判定しない。

## 用語の訂正

今回追加した646個は **スコープ**。エージェントが完了報告で「ファセット」と呼んだのは誤り。

[用語辞書のfacet定義](../00_Home/Glossary.md#25-facetプロジェクト観点) は「PJ直下の第一階層で、PJの一側面として意味的に凝集するスコープ」に限る。独立図の取り込みやスコープ化だけでは、その条件を満たしたことにならない。入力時の呼称をそのまま報告へ引き継ぎ、適用条件を確認しなかったことが誤用の原因。今回の取り込み記録もスコープ表記へ訂正する。
