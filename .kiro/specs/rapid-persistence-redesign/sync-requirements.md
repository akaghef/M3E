# 複数端末の同期の要件（案）

2026-11-19。状態: 案。11 節の問いには akaghef が答えた（同日）。[同期の思想](sync-principles.md)と DB 仕様書（`docs/03_Spec/Database_Spec.md`）を、検証できる要件の形に詰めたもの。

- 外部の model（GPT-6 Pro）と 2 往復して詰めた。1 往復目で要件の穴・決定どうしの矛盾・目次を出させ、2 往復目でこちらの回答を反映させて EARS 形式で書かせた。
- 本書の ID（R は要件、Q は akaghef に決めてもらう問い、K は未決の事項）は、本書を書いた会話の中の住所である。
- 各要件の「根拠」は次のとおり。
  - **決定**: akaghef の決定、または同期の思想から導いて本書を書いた session が決め、akaghef に報告したもの。
  - **仮決め**: 暫定として採ったもの。後から変える前提である。対応する問いを（Q1）の形で添える。見出しの【仮依存】は仮決めに依存する要件、【保留】は追加の協議まで実装しない要件。
  - **推論**: 決定から導いたもの。
- 受入条件は試験の定義であり、実施の結果ではない。試験で与える期限・容量・番号は fixture で、製品の既定値ではない。

**確定点は、remote の journal への fsync のままとする（Q1 で (b) を暫定に採った）。** remote の保存媒体を失えば、どの local にもまだ配られていない確定は失われうる。その代わり、復旧した地点と、欠けたかもしれない範囲を示す。二媒体での保全は、複雑さを避けるため当面は持たない。

## 1. 目的・適用範囲・保証の限界

### R1.1　workspace ごとの接続状態

**要件：** WHEN 接続状態を表示するとき、THE viewer SHALL workspace ごとに、push・pull 可能、remote 到達不能、remote に到達するが同期を拒否される状態を区別し、未送信件数を独立して表示する。  
**受入条件：** workspace S の remote を切断し、T の remote は到達可能だが権限拒否にする。S は到達不能、T は同期拒否として表示される。未送信件数をゼロにしても、接続状態や pull 完了の判定は変わらない。  
**根拠：決定**。

### R1.2　閲覧専用端末

**要件：** WHERE 閲覧専用端末として動作する場合、THE viewer SHALL workspace の clone を作らず remote への問い合わせで閲覧し、編集 Command を発行しない。  
**受入条件：** 閲覧専用端末から node を表示する。remote 切断後の新しい問い合わせは利用不能となり、local clone への切替や編集受付は起きない。表示済み画面が残る場合も、取得済みであることと接続状態を区別できる。  
**根拠：決定**。

### R1.3　検証の前提と保証範囲

**要件：** THE local SHALL 正しい権威として扱う remote が提示した履歴 ID・epoch・検証対象の到達地点を基準に、受信内容の欠損・破損・取り違えを検証する。  
**受入条件：** 同じ到達地点を指定した応答について、途中の記録を除去した場合、内容を変更した場合、別履歴の記録へ置換した場合はいずれも検証が失敗する。正当な workspace 番号の欠番が非公開 scope の更新に由来することだけを理由に、同期を失敗させない。  
**根拠：決定**。remote 自身の equivocation 検出と、権限外 scope の更新量の秘匿は保証対象外。

### R1.4　branch を作らない方針

**要件：** WHERE branch を持たない方針が適用される場合、THE remote SHALL 同一 workspace の現行の確定系列を一つに限定し、競合した Command を別 branch の確定として処理しない。  
**受入条件：** 二つの local が同じ欄を競合する値へ編集して push する。競合は未解決状態として残り、別 branch は生成されない。明示的な再構築による履歴 ID の更新は、旧履歴との対応を残して処理される。  
**根拠：決定**（Q10）。

## 2. データモデル・識別・不変条件

### R2.1　確定状態の構造不変条件

**要件：** WHEN Command を確定しようとするとき、THE remote SHALL 直前の確定を適用した状態に対して、root 以外の node の parent edge がちょうど一本であり、parent edge に循環がないことを検査し、違反する結果を確定しない。  
**受入条件：** 同じ親の子 A・B・C に対し、順に A を B の子、B を C の子、C を A の子へ移す。最初の二件が成立した場合、最後の一件は確定せず、適用済み状態にも復旧後の状態にも循環がない。  
**根拠：決定**。

### R2.2　識別と所属変更

**要件：** WHEN 既存 node の label・兄弟順・親・scope 所属を変更するとき、THE remote SHALL 対象の同一性を維持し、別 node の生成として処理しない。  
**受入条件：** node N を参照する alias を作り、N の label と親を変更する。alias の参照先 ID は N のままである。別 node の作成要求で既存 N の ID を使用しても、N が上書きされない。昇格による新 ID の作成は R8.6 に従う。  
**根拠：推論**（Q3）。

### R2.3　relation edge・alias の非所有性

**要件：** WHEN relation edge または alias を作成・変更・除去するとき、THE remote SHALL その操作に明示された別の構造変更がない限り、参照対象の親・所属・兄弟順を変更しない。  
**受入条件：** T に属する N を S の alias から参照し、S から N への relation edge を作成する。両者を除去しても、N の所属・parent edge・兄弟順は変化しない。  
**根拠：決定**。

### R2.4　scope 境界を跨ぐ移動【保留】

**要件：** IF Command が node を別の scope の部分木へ移す場合、THEN THE remote SHALL その Command を確定せず、未対応の操作として拒否する。  
**受入条件：** S の node を T の部分木へ移す Command を push する。確定されず、S・T とも変化しない。拒否の理由が「scope をまたぐ移動は未対応」と分かる。同じ scope の中の移動は通常どおり確定する。  
**根拠：決定**（Q3）。scope をまたぐ移動は当面実装しない。移動後の所属・共有範囲・保持の扱いは、実装するときに改めて決める。

### R2.5　観測した集合を基準にする削除

**要件：** WHEN 削除 Command を評価するとき、THE remote SHALL 観測した対象集合と所属条件を検査し、未観測の追加・所属変更を巻き込む場合は削除全体を conflict にする。  
**受入条件：** local A が部分木 P の削除を準備した後、local B が P に子 X を追加して確定する。A の削除を push すると、P の一部だけが消えることなく、削除全体が conflict になる。X は残る。  
**根拠：決定**（Q2）。

### R2.6　ロック

**要件：** WHILE node または scope にロックが掛かっている間、THE remote SHALL その対象を消す Command と、その対象の parent edge を変える Command を確定しない。
- 判定は、確定のときに remote が作る `touched` で行い、Command の種類によらない。dissolve・join・祖先の削除・unscopen・Undo・取り込みのどれで対象が消える場合も止める。
- ロックは掛けた node（出現）だけに効き、子孫には及ばない。内容の編集、子の追加、兄弟順の変更、祖先の付け替えは止めない。
- alias で同じ実体が複数の場所に出現するとき、ロックは出現ごとに付く。実体を終える操作・取り消す操作は、どれかの出現がロック中なら確定しない。
- ロックを掛ける・外すのは、その scope を編集できる human である。外すのは確認を挟んだ明示の操作一回で、承認を要しない。掛ける Command と外す Command はどちらも journal に記録し、Undo できる。ロックは対象に付き、掛けた人が権限を失っても残る。
- AI agent はロックを掛けられる。外せるのは、その scope での許可（grant）があるときだけである。
- ロックで確定しなかった Command には、`commandId` ごとに `LOCKED` の結果を返す。

**受入条件：**
- map の root にロックを掛け、root の削除を push する。確定されず、root は残る。ロックを外す Command を確定した後なら、同じ削除は通常の規則で評価される。
- ロックした node X の親 P を削除する Command は確定されない。X の子 Y の削除、X の内容の編集、X への子の追加、X の兄弟順の変更、P を別の親へ移すことは確定される。
- X を含む部分を dissolve して X が消える Command は確定されない。
- 実体 E が出現 A（ロック中）と出現 B に置かれているとき、B から E を終える Command は確定されない。B だけを面から外す操作は確定される。
- ロックを外す操作は、掛けた本人にも、その scope を編集できるほかの human にもできる。掛けた人の編集権限を外した後も、ロックは残り、ほかの編集者が外せる。
- 許可のない AI agent がロックを外す Command を push すると拒否される。

**根拠：決定**（Q5、Q11〜Q17）。誤操作による危険な操作（root の削除など）を防ぐための仕組みで、権限の代わりではない。Miro のオブジェクトの普通のロック（編集者なら誰でも外せる）に倣う。特定の人しか外せないロック（Miro の Protected Lock に当たるもの）は作らず、必要なら scope の権限で扱う。外せる人を編集者全体にするのは、掛けた人がいなくなって誰も外せなくなることと、外すのが承認待ちで止まることを防ぐためである。部分木に及ばせないのは、root に掛けたとき map 全体の削除と移動を止めてしまうからである。部分木に及ぶロックは後から足せる（欄の追加で、format は上げない）。

### R2.7　AI agent への解除の許可

**要件：** THE remote SHALL AI agent がロックを外す Command を、その scope に有効な許可があるときだけ確定する。
- 許可は scope の権限と同じ場所に置く。scope、許可される相手（アカウント）、許可の種類（接頭辞つきの開いた集合、例 `m3e:unlock`）、許可した human、任意の期限を持つ。付与も取り消しも Command である。
- 許可は与えた scope の中だけで効き、入れ子の scope に継承しない。
- 有効とは、確定の時点で、期限内であり、許可した human がその scope を今も編集できることである。
- 取り消しは許可のレコードの削除である。誰が許可していたかは journal の保持期間（archive の 90 日）だけ追える。
- ロックを外す Command を出した human と、許可した human が同じであることは求めない。

**受入条件：**
- scope S で AI agent A に許可を与える。A は S のロックを外せる。S の子 scope のロックは外せない。
- 許可の期限を過ぎた後、または許可した human の S の編集権限を外した後に A が push したロック解除は拒否される。
- 許可を取り消した後の A のロック解除は拒否される。

**根拠：決定**（Q13、Q18〜Q21）。継承をいま決めるのは、後から継承を足すと既存の許可の意味が変わるからである。許可した human の権限で効力を判定するのは、許可が権限の委譲だからである（ロックそのものは掛けた人の権限によらず残る）。

## 3. 権限・可視性・情報の開示

### R3.1　現在の権限による取得・確定判定

**要件：** WHEN pull または Command の確定を処理するとき、THE remote SHALL 当該処理に適用される現在の権限に基づいて認可し、過去に clone・編集できたことを認可の代用にしない。  
**受入条件：** local A が S を clone して編集した後、remote で A の権限を失効させる。再接続後の pull は新しい S の内容を返さず、書込権限を失った Command は確定しない。失効前に作られた outbox は、それだけを理由に消去されない。  
**根拠：決定**（Q4）。

### R3.2　人・AI ごとの local の視界

**要件：** WHEN 人または AI agent の問い合わせを処理するとき、THE local SHALL local が保持する権限状態に従って当該主体の可視範囲を適用し、端末内にデータが存在することを開示許可とみなさない。  
**受入条件：** local に S・T の両方が存在し、AI agent は S だけを閲覧可能とする。T を明示指定した問い合わせ、検索、関連情報取得でも T の内容は返らない。viewer の非表示設定を解除しても、この判定を迂回できない。  
**根拠：推論**。offline 中に未受信の失効は R3.5 の保証範囲に従う。

### R3.3　入れ子の scope の権限【保留】

**要件：** 未定。祖先の拒否と子の許可のどちらを優先するかは、追加で協議する。  
**受入条件：** 協議の後に書く。  
**根拠：** Q7。全体を非公開にして一部を公開する使い方もあるため、「祖先の拒否は子で覆せない」とは決めていない。

### R3.4　relation edge の所属と開示【仮依存】

**要件：** WHEN relation edge を表示・配送するとき、THE remote SHALL 両端が同じ scope にある relation edge だけを可視化の対象とし、両端の scope が異なる relation edge の内容を配送しない。履歴の格納先は source の scope とする。  
**受入条件：** 両端が S にある edge は、S を読める主体に表示される。source が S、target が T の edge は、S・T の両方を読める主体にも表示されず、問い合わせ・snapshot・journal の配送・conflict 表示のいずれからも label が届かない。  
**根拠：仮決め**（Q8）。後から変える前提である。

### R3.5　offline 中の失効

**要件：** WHILE local が remote の権限失効を受信していない offline 状態にある間、THE local SHALL 取得済み内容の利用と local commit を継続可能とし、それらが remote で確定可能であるとは表示しない。  
**受入条件：** local を切断してから remote で権限を失効させる。切断中の local commit は outbox に保存できる。再接続後には R3.1 に従って拒否され得る。切断中に閲覧できたことを権限機構の試験失敗とは扱わない。  
**根拠：決定**（Q4）。

### R3.6　conflict の解決権限

**要件：** WHEN conflict 解決 Command を評価するとき、THE remote SHALL 影響する全 scope の必要権限を現在持つ編集者による解決を認め、原作者であることだけを必須条件にしない。  
**受入条件：** S・T に跨る conflict に対し、S だけの必要権限を持つ編集者の解決は確定しない。S・T の必要権限を持つ別の編集者による解決は、他の前提条件を満たせば確定できる。  
**根拠：決定**（Q5）。

## 4. Command の契約

### R4.1　local commit の耐久性

**要件：** WHEN local commit を完了通知するとき、THE local SHALL Command の内容・`commandId`・依存を outbox に fsync 済みとし、永続化に失敗した操作を完了扱いにしない。  
**受入条件：** fsync 後・通知前に process を停止して再起動すると、同じ ID・内容・依存の Command が復元される。容量不足を注入して fsync を失敗させた場合、完了通知は出ず、未保存であることが判別できる。  
**根拠：決定**。

### R4.2　Command ID と内容の対応

**要件：** IF 同一 `commandId` に対して内容同一性の規約上異なる内容が要求された場合、THEN THE remote SHALL 要求を拒否し、既存の Command・結果・依存関係を上書きしない。  
**受入条件：** ID C で N の label を変更した後、ID C のまま対象を M に変更して送る。後者は拒否され、M は変化せず、C の照会結果は最初の Command に対応する。  
**根拠：決定**。

### R4.3　Command の不可分性

**要件：** WHEN 一つの Command を確定・適用するとき、THE remote SHALL 当該 Command の変更を不可分に扱い、Command 内部の一部だけを確定結果にしない。  
**受入条件：** 親変更と scope 所属変更を含む移動について、DB transaction の途中で故障を注入する。復旧後は、未確定なら変更前、確定済みなら移動全体の適用後になり、旧 parent edge だけが失われた状態を現行状態として公開しない。  
**根拠：決定**。

### R4.4　宣言された依存

**要件：** WHILE 宣言された依存先が reject・park、または成立を確認できない状態にある間、THE remote SHALL その依存を必要とする後続 Command を実行しない。  
**受入条件：** A、A に依存する B、B に依存する C、独立した D を送る。A が park されると B・C は実行されず、D は自身の条件を満たせば確定できる。依存を宣言していない意味的関係の自動推定は合否条件に含めない。  
**根拠：決定**（Q5）。

### R4.5　有限の再送窓と結果照会

**要件：** WHEN 同一 Command が有効な再送窓内で再送されたとき、THE remote SHALL 保存された確定結果を利用して重複実行を防ぎ、記録が存在しないという理由だけで未確定と断定しない。  
**受入条件：** 確定後の応答を破棄し、compaction と再起動を挟んで同じ ID を再送する。再送窓内では変更が二重に生じず、元の確定結果を取得できる。期限後に結果が確認できなければ、未処理の証拠として扱わない。  
**根拠：決定**。

### R4.6　結果不明 Command の保留

**要件：** IF 再送期限後に元の Command の結果を確認できない場合、THEN THE local SHALL 当該 Command を保留し、自動的に新しい ID を付けて再発行しない。  
**受入条件：** 応答を失った Command を、結果記録が確認できない期限後に復帰させる。snapshot の再取得、アプリの再起動、再接続を行っても新 ID の Command は生成されず、元の内容と結果不明の状態が残る。  
**根拠：決定**。

### R4.7　Command の解釈と前提条件

**要件：** WHEN Command を評価するとき、THE remote SHALL 対応する Command schema と意味規約に従って対象・比較単位・前提条件・依存を解釈し、解釈不能な部分を推測して実行しない。  
**受入条件：** 未対応の比較対象パスまたは Command schema を送ると、状態を変更せず、未対応箇所を返す。対応済みの label 編集は、別 attribute の変更だけを理由に node 全体の rev で競合させない。  
**根拠：推論**。

## 5. 確定・永続化・再生

### R5.1　remote の保存媒体の喪失

**要件：** IF remote の保存媒体が失われた場合、THEN THE remote SHALL 届く local と backup から復旧した地点と、欠けたかもしれない確定の範囲を示し、欠けがないと確認できない復旧を完全な復旧と表示しない。  
**受入条件：** 確定 101 を fsync した後、どの local も 101 を pull しないうちに remote の媒体を失わせる。復旧の結果は「100 まで復旧、101 以降は欠けた可能性がある」と表示され、完全な復旧とは表示されない。  
**根拠：決定**（Q1、暫定）。複雑さを避けるため、媒体 1 つの喪失で確定を失わない保証は当面持たない。

### R5.2　確定応答の条件

**要件：** WHEN 確定成功の応答を返すとき、THE remote SHALL その確定の journal への fsync と、その確定までの engine への適用を完了している。  
**受入条件：** fsync の前に停止すると成功応答は出ない。fsync の後、engine への適用の前に停止しても成功応答は出ない。両方の完了後に成功応答を返した場合、その後の問い合わせは当該確定より古い状態を返さない。  
**根拠：決定**（Q1）。

### R5.3　未適用の確定と直列検査

**要件：** WHILE 確定済みだが engine 未適用の記録が存在する間、THE remote SHALL 古い engine 状態を用いて後続 Command を確定せず、先行する確定の適用を回復する。  
**受入条件：** 値 `0→1` の確定記録を保存後、engine 適用前に故障させる。その間に前提値 `0` の別 Command を送る。復旧後は `1` を含む状態で評価され、未適用だった `0` を根拠に確定されない。  
**根拠：決定**。

### R5.4　確定結果の再生

**要件：** WHEN journal を replay するとき、THE remote SHALL 確定時に採用した変更・生成 ID・兄弟順キー・resolution を再現し、現在の merge 規則で過去の意図を再判定しない。  
**受入条件：** キー衝突を解消して確定した履歴を保存し、衝突解消規則を変更してから replay する。確定済みのキー・順序・ID・解決結果は変更前と一致する。  
**根拠：決定**。

### R5.5　復旧対象となる管理状態

**要件：** WHEN snapshot と journal から復旧するとき、THE remote SHALL 内容に加えて、権限、未解決 conflict、必要な Command 結果、epoch・履歴 ID、端末失効、消去状態を回復する。  
**受入条件：** 権限失効、conflict 登録、Command 確定、端末失効を順に行った後、engine の保存内容を失わせて復旧する。各状態と依存の停止が再現され、旧権限や失効端末が復活しない。  
**根拠：決定**。

### R5.6　snapshot の自己完結性と到達地点

**要件：** WHEN snapshot を復旧用として公開するとき、THE remote SHALL 対象範囲・履歴 ID・epoch・到達地点・検証情報・必要な構成要素を特定可能にし、未完成の snapshot を有効な復旧基点として公開しない。  
**受入条件：** snapshot の生成途中で停止するか、構成要素の一つを除去する。復旧時に不完全性が検出され、その snapshot を基点とした復旧完了にはならない。完全な snapshot と後続 journal では、対応する状態を再構成できる。  
**根拠：推論**。

### R5.7　local engine の再構成

**要件：** WHEN 各端末の engine を再構築するとき、THE local SHALL 確定状態を保持する scope ごとの snapshot と確定記録から再構成し、未確定の意図は outbox に基づいて区別して復元する。  
**受入条件：** local の engine データだけを削除し、snapshot・journal・outbox を残して再起動する。確定状態と pending の区別が復元され、pending が確定済みとして再登録されない。  
**根拠：決定**。journal と snapshot が durability authority（system of record）、各端末の Neo4j が semantic authority であり、Neo4j は replay で再構築する。特定の DB 製品・native dump 形式には依存しない。

## 6. push・pull・部分複製

### R6.1　手動同期

**要件：** WHILE 手動同期の方針が適用される間、THE local SHALL local commit を理由とする自動 push・自動 pull を開始せず、明示的な同期要求に対応して処理する。  
**受入条件：** online の local で編集し、同期操作を行わず待機する。remote の状態は変わらない。明示的な push 後に初めて当該 Command が remote へ送信される。  
**根拠：決定**。

### R6.2　abort の事前検証

**要件：** WHEN push の処理を開始するとき、THE remote SHALL 当該要求全体の epoch・履歴 ID・hash 鎖に関する abort 条件を、最初の Command の確定前に検証する。  
**受入条件：** 複数 Command の push の末尾に不正な検証情報を置く。先頭から途中までの Command も確定せず、要求全体が abort する。同じ検証情報に対する判定を、前半の確定後まで遅らせた実装は不合格とする。  
**根拠：決定**。

### R6.3　Command 間の partial acceptance

**要件：** WHEN abort 条件を通過した push を処理するとき、THE remote SHALL Command ごとに結果を確定し、ある Command の conflict・reject だけを理由に独立した Command を停止しない。  
**受入条件：** A が conflict、B が A に依存、C が独立かつ妥当な要求を送る。A は conflict、B は未実行、C は確定となり、それぞれの結果を ID に対応付けて取得できる。  
**根拠：決定**および**推論**。

### R6.4　処理途中の故障

**要件：** IF push の処理途中に process 停止・通信断・fencing による継続不能が発生した場合、THEN THE remote SHALL 既に成立した確定を維持し、未確定部分と区別して照会可能にする。  
**受入条件：** 最初の二 Command の確定後、三番目の確定前に停止する。復旧後、最初の二件は一度だけ成立しており、三番目は確定済みと偽って返されない。要求全体を未処理として再実行しない。  
**根拠：推論**。これは事前検証による全体 abort とは区別する。

### R6.5　scope 単位の複製と配送内容

**要件：** WHEN clone・snapshot・確定記録を配送するとき、THE remote SHALL 複製対象の scope と主体の開示権限を適用し、許可されない内容を client 側の表示制御だけに委ねない。  
**受入条件：** S だけを clone する端末への応答と保存された受信内容を検査する。T の本文や、R3.4 により開示不可の edge 内容が含まれない。viewer に表示されないだけでは合格にしない。  
**根拠：決定**。relation edge の部分は**仮決め依存**（Q8）。

### R6.6　scope ごとの検証と古い prefix の扱い

**要件：** WHEN scope の snapshot または確定記録を取り込むとき、THE local SHALL scope 内の順序と hash 鎖を、履歴 ID・epoch・scope ID・基点・取得対象の到達地点に対応付けて検証する。  
**受入条件：** 中間記録の欠落、順序交換、別 scope の記録混入は取り込まれない。有効な古い prefix だけが返された場合も、要求した到達地点に届いていなければ同期完了としない。検証済みの既存状態は維持する。  
**根拠：決定**。

### R6.7　所有・権限変更の公開と複数 scope の断片

**要件：** WHEN 所有関係または権限に関わる一確定を複数 scope の断片として取り込むとき、THE local SHALL 必要な可視部分が揃うまでその途中状態を通常状態として公開せず、同じ `commandId` の別断片を重複として捨てない。  
**受入条件：** S・T を clone し、N の S→T 移動について T 側を先に受信する。N が二つの親を持つ状態を通常表示しない。S 側の到着後に移動全体が反映され、両断片の再送で二重適用されない。T が複製対象外なら、必要な可視部分の範囲に従って処理する。  
**根拠：決定**。

### R6.8　dangling reference

**要件：** IF 参照先が現在の複製状態に存在しない場合、THEN THE local SHALL 未取得・削除済み・権限外の判定を混同せず、判定不能であることだけを理由に参照元を削除・移動しない。  
**受入条件：** S の alias が未 clone の T を参照する。alias は失われず、参照先を利用できない状態として扱われる。後に許可された T を取得すると、参照元への編集 Command を追加せずに参照を解決できる。開示不可の理由は利用者へ漏らさない。  
**根拠：決定**。

### R6.9　保持期間を越えた local の再取得

**要件：** WHEN 必要な確定記録が保持対象外になった scope を更新するとき、THE local SHALL その scope の検証済み snapshot を基点に取り直し、outbox を保全したまま前提条件と元の Command の結果を再照合する。  
**受入条件：** local を保持期間より長く停止させ、その間 remote で compaction する。再取得後も未送信・結果不明の Command は残る。古い意図の前提値を黙って現在値へ変更したり、結果不明の Command に新 ID を付けたりしない。  
**根拠：決定**。

## 7. merge・conflict・Undo

### R7.1　欄ごとの compare-and-set

**要件：** WHEN 通常の代入 Command を評価するとき、THE remote SHALL 対象欄の現在値が変更前値と一致すれば適用可能とし、変更後値と一致すれば実差分なしとして扱い、どちらとも一致しなければ conflict にする。  
**受入条件：** 前提 `a`、変更後 `b` の要求について、現在値 `a` なら `b`、現在値 `b` なら実差分なし、現在値 `c` なら conflict となる。途中に `a→x→a` があっても、現在値 `a` なら適用可能である。  
**根拠：決定**（Q9）。認可・存在・構造など他の前提条件は別に検査する。

### R7.2　実差分なしの結果と変更所有関係

**要件：** WHEN Command が変更後値との一致により実差分なしとなったとき、THE remote SHALL その結果を実際の変更と区別して記録し、その Command が値を作った証拠として扱わない。  
**受入条件：** B が `a→b` を確定した後、A が同じ `a→b` を送る。A は実差分なしとして照会できる。再起動・再送後も A の実差分は増えず、A の Undo により B の変更が取り消されない。  
**根拠：推論**（Q9）。

### R7.3　Undo の証拠

**要件：** WHEN Undo を評価するとき、THE remote SHALL 元の Command が実際に作った値・状態が残っている証拠と、Undo 時点の必要条件を検査し、証拠がない場合は内容を巻き戻さない。  
**受入条件：** A が `a→b`、B が `b→c→b` を確定した後、A の Undo を送る。現在値が `b` でも取り消さない。別欄だけが変更され、対象欄について A の変更が残る証拠がある場合は、node rev の増加だけでは拒否しない。証拠を除去した試験でも値一致だけで通さない。  
**根拠：決定**（Q9）。

### R7.4　並べ替えと node の存在

**要件：** WHEN 並べ替え Command を評価するとき、THE remote SHALL node の存在・所属を並べ替えの副作用として変更せず、同じ対象の競合する並べ替えでは後の確定を採用し、削除済み対象の並べ替えは効果なしとする。  
**受入条件：** 旧兄弟一覧に基づく並べ替えより前に、新しい子 X を確定する。並べ替え後も X は残る。同じ node への二つの並べ替えでは確定順に従い、端末時計を逆転させても結果は変わらない。対象削除後の並べ替えでは node を復活させない。  
**根拠：決定**。

### R7.5　兄弟順キーの衝突

**要件：** WHEN 同じ兄弟順キーを持つ別の子を確定するとき、THE remote SHALL 後から確定する側のキーを作り直し、両 node を保存して、キー衝突だけを理由とする conflict・作成拒否・利用者通知を発生させない。  
**受入条件：** 二つの local が同じ親・同じキーで異なる子を作成して push する。両方が存在し、確定後のキーは衝突せず、再生後も同じ順序になる。  
**根拠：決定**。

### R7.6　conflict と解決 Command

**要件：** WHEN conflict の登録または解決を確定するとき、THE remote SHALL 元の Command を識別できる状態を保持し、解決を別 Command として記録し、依存 Command の再評価結果を追跡可能にする。  
**受入条件：** conflict 登録後に engine を再構築しても、元の ID・理由・未実行の依存を取得できる。異なる解決を同時に送っても、解決済み状態を無視して二重に適用しない。元の ID の内容を書き換える方法では解決できない。  
**根拠：決定**（Q5）および**決定**。

### R7.7　未定義の merge case

**要件：** IF 対応済み Command の競合 case に適用可能な確定済みの解決規則がない場合、THEN THE remote SHALL 自動解決を推測せず、当該 Command とその依存を実行せずに人の判断へ返す。  
**受入条件：** merge 表で意図的に未定義にした競合 case を入力する。暗黙の LWW や一括上書きは行われず、独立した Command だけは処理できる。型の組合せに規則があっても、構造検査違反を通さない。  
**根拠：決定**。

## 8. 履歴・保持・昇格・消去

### R8.1　scope の保持方針

**要件：** WHEN 設定された時間または容量の保持条件に基づいて履歴を削減するとき、THE remote SHALL 破棄可能な履歴だけを対象とし、現在の状態と未解決 conflict を保持期限で削除しない。  
**受入条件：** 短い時間上限と容量上限を設定し、各上限を別々に先に到達させる。対象となる過去履歴は削減対象になるが、現在の node と未解決 conflict は残る。node の期限削除を明示有効化していなければ、履歴期限による node 削除は起きない。  
**根拠：決定**。

### R8.2　local の未処理内容の保持

**要件：** WHILE 未送信・結果不明・park 中、または確定内容の取り込み待ちである Command を保持している間、THE local SHALL 履歴の保持期限を理由に必要な outbox 内容・依存・結果照合情報を破棄しない。  
**受入条件：** 上記の状態をそれぞれ作成し、履歴期限を越えて再起動する。各 Command の内容と状態を復元できる。容量不足時にも、完了済み local commit を黙って削除して空きを作らない。  
**根拠：決定**。

### R8.3　共有履歴と容量計上

**要件：** WHEN 複数 scope に関わる履歴を保持・計上するとき、THE remote SHALL いずれかの scope に保持義務が残る記録を維持し、その scope 単独で破棄できる履歴の容量と共有履歴の容量を分け、計測範囲を明示した workspace 使用量を示す。  
**受入条件：** Rapid と全版保持の Deep に跨る記録を作り、Rapid の上限を超える。Deep の保持義務がある記録は消えず、Rapid の単独破棄可能容量に混ぜて表示されない。共有領域と全体使用量の計上範囲を照合できる。  
**根拠：決定**。

### R8.4　継承による保持期間の短縮【保留】

**要件：** 未定。入れ子の scope の継承の規則（R3.3）と合わせて協議する。保持期間の短縮が確認つきの明示操作であることは決定済み（R8.1 の前提）。  
**受入条件：** 協議の後に書く。  
**根拠：** Q7。

### R8.5　Deep の全版保持と retraction

**要件：** WHILE Deep の全版保持が適用されている間、THE remote SHALL 消去対象を除く各版を保持し、内容の廃止を過去版の破棄ではなく retraction として記録する。  
**受入条件：** 三つの版を作成して retraction する。通常表示上の廃止状態と過去三版を確認できる。現在版だけを含む snapshot を作成しても、それだけを理由に過去版を破棄しない。  
**根拠：決定**。領域ごとの具体的な既定設定は未決。

### R8.6　Rapid と Deep【保留】

**要件：** 未定。Rapid か Deep かは scope ごとに決める。Rapid と Deep の違い、昇格の意味（新しい ID への複製か、scope の区分の変更か）は追加で協議する。  
**受入条件：** 協議の後に書く。  
**根拠：** Q6。

### R8.7　compaction の安全条件

**要件：** WHEN journal を snapshot に畳み込み旧記録を破棄するとき、THE remote SHALL 復旧・同期・有効な再送窓・保証中の履歴利用に必要な情報が残ることを検証してから破棄する。  
**受入条件：** snapshot 作成途中に停止しても、従来の復旧経路は失われない。compaction 後に、確定状態の復旧、再送窓内の重複排除、保持対象の過去版取得を検証できる。最新状態だけを再生できても、必要な過去版が失われれば不合格とする。  
**根拠：推論**。開始契機は未決。archive に移した journal は、その範囲を覆う snapshot の検証が通っていれば 90 日で削除する（決定）。

### R8.8　消去と旧 snapshot からの復旧

**要件：** WHEN crypto-shredding の成功を通知するとき、THE remote SHALL 管理対象内の消去対象を復号不能にし、旧 snapshot・backup からの復旧によって再び読める状態にしない。  
**受入条件：** 消去前の snapshot と backup を保存し、対象の消去成功後にそれらから復旧する。消去対象は読めず、消去状態を確認できない復旧は完了しない。消去対象外のデータは、その復旧保証に従って利用できる。  
**根拠：決定**。取り出し済み平文の除外は**決定**（Q4）。管理対象と鍵の消去単位は K4。

## 9. 運用・復旧・移行

### R9.1　旧 remote の fencing

**要件：** WHEN 新 remote を確定権限のある remote として有効化するとき、THE remote SHALL 旧世代が以後の確定を成立させられない条件を満たし、その条件を確認できないまま切替完了にしない。  
**受入条件：** 旧 remote と旧 client を分断したまま新 epoch だけを発行する。旧側で確定を続けられるなら切替は不合格となる。fencing 成立後は、旧側への要求から新たな有効な確定が生じない。  
**根拠：決定**。

### R9.2　workspace 復旧の完全性

**要件：** WHEN workspace を再構築するとき、THE remote SHALL 必要な scope・確定記録・管理状態の被覆と整合を検証し、local ごとの最大番号だけを根拠に完全な復旧と判定しない。  
**受入条件：** S の最新コピーと T の古いコピーだけを提供し、T に必要な確定を欠落させる。最大番号が大きくても復旧完了にはならない。必要なコピーが揃った場合にだけ、復旧した地点と新しい履歴 ID・epoch を対応付けて完了する。  
**根拠：推論**（Q1）。

### R9.3　remote の明示的な移動

**要件：** WHEN remote の移動を実行するとき、THE remote SHALL 対象 workspace、移動先、引き継ぐ状態、fencing の成立を明示的な移動操作に対応付け、検証前の移動先を確定先として有効化しない。  
**受入条件：** 古いコピーを持つ移動先を指定する。状態検証が完了するまで切替完了にはならない。切替中も local commit は続けられ、その outbox が消去されたり自動的に別 workspace へ送られたりしない。  
**根拠：決定**。

### R9.4　端末の clone・backup 復元

**要件：** WHEN clone または backup から local を新たに成立させるとき、THE local SHALL 新しい端末 ID を使用し、復元した既存 Command の ID・内容・依存を維持する。  
**受入条件：** 一つの backup から二つの local を復元する。端末 ID は互いに異なり、保存済みの同じ Command は同じ ID のままである。新規 Command の発行が、既存 outbox の ID 再発行を伴わない。  
**根拠：決定**。

### R9.5　非互換 client の停止と変換

**要件：** IF client が互換範囲外である場合、THEN THE local SHALL push を停止し、outbox の原内容を保全したまま更新・変換を行い、意味や前提条件の変更を同じ Command の単なる再送として扱わない。  
**受入条件：** 旧 client に未送信 Command を残して互換範囲を更新する。push は停止し、更新を失敗させても原内容が残る。変換で対象値の意味が変わる場合、同じ ID のまま実行されない。元の結果が不明なら新 ID の自動発行も行われない。  
**根拠：決定**。

### R9.6　規則変更と過去の確定

**要件：** WHEN schema・merge・権限・保持などの規則を変更するとき、THE remote SHALL 過去の確定内容を新規則で黙って再解釈せず、保持対象の履歴について従来の確定結果を復元可能にする。  
**受入条件：** 仮決めの規則を変更した後に、変更前の snapshot・journal を replay する。元の確定値と解決結果は変わらない。新規則による現在状態の変更が必要なら、別の明示的な変更として識別できる。  
**根拠：推論**。

### R9.7　local の旧 backup と消去状態

**要件：** WHEN 旧 backup から local を復元するとき、THE local SHALL 消去対象を再公開しないために必要な消去状態を確認し、確認不能な対象を通常の閲覧可能状態として有効化しない。  
**受入条件：** 消去前の backup を、消去後に offline で復元する。必要な消去状態や復号可否を確認できない対象は公開されない。確認後も消去済み対象は読めない。既存 local の offline 継続と、旧 backup の復元を同一の許可根拠で処理しない。  
**根拠：推論**。取り出し済み平文の例外は R8.8 に従う。

## 10. 性能・観測可能性・受け入れ条件

### R10.1　測定条件と未決の目標値

**要件：** WHEN 性能を測定するとき、THE local SHALL dataset、node 数、本文量、Command の種類と大きさ、outbox 件数、並列度、機材・ソフトウェア構成、回線条件を固定・記録し、楽観表示・local 永続化・remote 確定・local 取り込みを別々に測る。  
**受入条件：** 同じ条件で再試行できる測定記録が得られる。応答を失敗・保留した要求を成功時の待ち時間だけから除外して評価しない。未承認の数値を SLO の合否基準として出力しない。  
**根拠：決定**。数値目標は未決。

### R10.2　対話応答の優先

**要件：** WHILE 大量投入が継続している間、THE remote SHALL 対話 Command の処理を優先し、後から来る大量投入だけによって対話 Command を無期限に追い越させず、実行中 Command の不可分性と依存順序を維持する。  
**受入条件：** 大量投入を途切れさせず、独立した小さな対話 Command を投入する。実行中 Command と必要な先行依存の完了後、対話 Command が処理される。処理待ちの原因を確認できる。時間上限の合否は、数値目標決定後に追加する。  
**根拠：決定**。単一 Command の受付上限は K10。

### R10.3　保存・確定・取り込み・未実行の表示

**要件：** WHEN 編集状態または同期結果を表示するとき、THE viewer SHALL local 保存済み、remote 確定済み、local 取り込み済み、結果不明、park・reject による未実行を区別し、確定取り込み前に対応する意図を表示から単純に消去しない。  
**受入条件：** push 成功応答を受けるが確定内容の取り込みを遅延させる。編集は消えず、取り込み待ちと分かる。後に取り込むと一度だけ確定表示へ移る。結果不明を未確定断定として扱わず、構造上適用できない pending を確定構造として表示しない。  
**根拠：決定**。

### R10.4　運用・監査情報

**要件：** WHEN 同期・復旧・競合処理の状態を問い合わせられたとき、THE remote SHALL 権限の範囲内で、確定地点・適用地点・scope ごとの到達地点、Command の結果、依存による停止理由、resolution、実行主体と端末、容量計測の範囲を確認可能にする。  
**受入条件：** DB 適用停止、応答喪失、依存 park、媒体喪失をそれぞれ注入する。どこまで確定し、どこまで適用され、何が未確認かを区別できる。復元端末の送信者情報と元 Command の由来を混同せず、権限外の本文が診断情報へ漏れない。  
**根拠：決定**および**推論**。

## 12. 1 往復目で分かった、決定どうしの緊張

- 「fsync で確定」と「届く local から最長の部分を集めて remote を作り直す」: どの local にも配られていない確定は local から戻せない。戻せた最長の部分と、全確定の保全は別である（Q1、K1）。
- 「scope だけを clone」と「全 local を集めた workspace の復旧」: どの local も持たない scope がありうる。最大の番号を集めても完全な workspace にはならない（R9.2、K8）。
- 「確定済み prefix の上に pending を重ねる」と「scope 間の consistent cut を保証しない」: 地点の違う scope を合成した確定状態は、一つの workspace prefix の状態とは限らない。scope ごとの到達地点を持つ部分状態として扱う（R6.6、R6.7）。
- 「Command 間の partial acceptance」と「不一致なら push 全体を abort」: 前半を確定した後で abort の条件が分かっても、前半は取り消せない。abort の条件は確定を始める前に検査し終える（R6.2）。
- 「複数 scope の op は最長の保持期間」と「scope ごとの容量上限」: 長期の保持義務を残したまま、短期側の使用量を必ず上限以下にはできない。共有の履歴は別に数える（R8.3、K9）。
- 「Deep の全版保持・journal の replay」と「crypto-shredding」: 消した内容の旧版を完全に戻す保証とは両立しない。消去を優先する（R8.8）。
