# 複数端末の同期の思想

2026-11-18、akaghef との対話で決めたことと、その価値観を記録する。[brief](./brief.md) の「物理配置の原則」（2026-11-16）を更新する。食い違う場合は本書が優先する。各節の末尾に、まだ決めていないことを分けて書く。

ここから導いた検証できる要件は [同期の要件](sync-requirements.md) にある。

## remote と local

Git の cloud と local の関係に倣う。

- remote は workspace ごとにちょうど一つ置く。置き場所は選べる（社内の一つの端末、外部のサービス）。特定の置き場所には固定しない。
- local は複数あってよい。どの local も server・engine・viewer を持ち、編集できる。
- 確定するのは remote である。local の commit は確定ではない。
- online とは、その local がその workspace の remote と push / pull できる状態をいう。online かどうかは workspace ごとに判定する。remote に届くのに拒否される状態は、online とは別の「同期の失敗」として扱う。まだ push していない件数は、online とは別の軸で示す。
- push / pull は当面は手動で行う。挙動を確かめるためである。
- 運ぶ経路は push / pull の一本だけにする。Syncthing はやめる。
- remote の移動は明示の操作で行う。remote が止まっていても、local は commit を続けられる。
- remote を作り直すときは、届くすべての local から、連続していて検証済みの最長の部分を集める。新しい履歴 ID と世代を発行し、古い remote には二度と書かせない。どこまで保全を確認できたかを画面に出す。
- 閲覧専用の端末（iPad など）は clone を持たず、remote に接続して読む。

これにより、物理配置の原則の「確定者（writer）を端末に固定する」「Mac mini を集約点にする」「他の PC は確定者へ Command を送る」を、remote と local の関係に置き換える。

## データの形

- Neo4j は正本エンジンで、ドメインモデルそのものを担う（DC39）。他の何かの写しではない。
- journal は確定の記録である。確定の順番、`commandId`、端末、世代、履歴 ID を持つ。復旧と push / pull に使い、engine には依存しない。
- 1 件の確定は、次の順に workspace ごとに 1 件ずつ処理する：Neo4j の上で検査する → journal に追記して fsync する（ここで確定）→ 同じ内容を transaction で Neo4j に適用する → 応答する。応答は適用の後に返すので、確定の直後に読めば新しい値が返る。
- 兄弟順キーは、parent edge（Neo4j の relationship）の property に置く。
- journal と端末の未確定の Command（outbox）は、当面 jsonl のまま置く。書きかけの行の後始末、scope ごとの pull や重複排除の検索の遅さ、outbox の不具合が繰り返し起きたら、SQLite への切り替えを検討する。

## 権限

- 権限の単位は scope とする。workspace では広すぎる。scope の権限が、人の閲覧範囲だけでなく agent の視界も決める。
- 複製の単位も scope とする。local は、権限のある scope だけを clone する。物理配置の原則の「複製の単位は workspace」を改める。

ここから導かれ、まだ確かめていないこと：

- scope ごとに番号と hash の鎖を持ち、local は scope ごとに pull して照合する。
- 権限の無い scope を指す alias や relation edge は、中身を出さない参照として表示する。
- 二つの scope にまたがる変更（scope をまたぐ移動など）には、両方の scope への書き込み権限が要る。
- 権限の変更も journal に記録する。外した後の local には消去を指示するが、すでに渡ったデータは回収できない。

未決：入れ子の scope に権限を引き継ぐかどうか（推奨：引き継ぐのを既定とし、子の scope で上書きできる）。

## merge の価値観

- node が存在することは、並び順より優先する。並び順を理由に、node の作成を拒否したり競合にしたりしない。別々の端末が作った子どうしの並びは、規則で機械的に決めてよい。
- 挿入とは、足してから並べ替えることである。挿入と並べ替えは別の操作として扱う。
- 並べ替えどうしがぶつかったら、後から確定した方を採る。並べ替えた node が削除済みなら、その並べ替えは消える。
- 同じ兄弟順キーが二つできたら、remote が確定の時に後から来た方のキーを作り直す。人には知らせない。端末がキーを作ってよいという record-schema の DA27 はそのまま保つ。
- merge の方針は、「操作の種類 × 操作の種類」の表として書き切る。各マスには「自動で合わせる」「規則で片方に決める」「競合として人に返す」のどれか一つを入れる。迷うマスはまず人に返し、実際に使ってうるさかったマスから自動にしていく。

未決：競合の判定の仕方。journal の設計の中で協議する（推奨：Command に変更前と変更後の値を持たせ、remote で今の値がどちらとも違うときだけ競合にする）。

## 過去の情報の残し方

過去の情報は目的ごとに要る期間が違う（復旧、同期、Undo、由来）。残し方は領域ごとに分ける。

- Flash：ほぼ残さない。
- Rapid：作業のしやすさを優先する。journal は保持期間（時間か件数）の分だけ残し、手放す前に snapshot を作る。remote は local の追いつきを待たない。保持期間より遅れた local は snapshot から clone し直し、未確定の Command は前提条件つきで push し直す。重複排除の記録は保持期間より長く残す。死んだ端末は明示の操作で登録から外す。
- Deep：Git のように積み上げる。版をすべて残し、版ごとに誰が・いつ・なぜを持つ。消すときは廃止の印を付け、私的な情報だけは読めなくする手段を用意する。遅れた local も差分を pull できる。
- Rapid から Deep への昇格が、Git の commit に当たる。それまでの細かい編集を意味のある一つの版にまとめ、理由を付けて Deep の履歴に積む。価値のある歴史を残すかどうかは、昇格のときに人か agent が判断する。

- 保持の方針は scope に付ける。scope ごとの log の保持期間を、時間と容量の二つの設定可能なパラメータで持つ（Kafka の topic ごとの `retention.ms` と `retention.bytes` に当たる）。どちらかの上限に先に達した分から手放す。Deep は時間・容量とも無制限を既定とする。
- この保持期間は履歴に掛かる。期限を過ぎて手放すのは過去の op と版で、今の状態は残す。node そのものを期限で消す設定は、別の属性として、明示的に有効にした scope にだけ付ける。
- 保持の方針は権限と同じ継承と上書きの規則で解決する。
- 複数の scope に関わる op は、関わる scope のうち最も長い保持期間で残す。
- 重複排除の記録は scope の保持期間に連動させず、workspace 単位で再送が来うる期間より長く持つ。
- 保持期間の短縮は、過去を即座に捨てる破壊的な操作なので、確認つきの明示の操作にする。
- 古すぎる local の判定と clone し直しは scope ごとに行う。

未決：各領域の保持期間の既定値（使ってから決める。Rapid の初期値の目安は 30 日）。scope をまたぐ relation edge の履歴をどの scope に属させるか（推奨：source の scope）。scope ごとの snapshot が参照先の欠けを許すか、scope 間の一貫した切断面を保証するか（推奨：参照先の欠けを許す）。
