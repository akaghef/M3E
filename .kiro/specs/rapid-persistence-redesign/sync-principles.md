ここから導いた検証できる要件は [同期の要件](sync-requirements.md) にある。2026-11-19 に同書 11 節の問いへの akaghef の回答を本書にも反映した。

## remote と local

Git の cloud と local の関係に倣う。

- remote は workspace ごとにちょうど一つ置く。置き場所は選べる（社内の一つの端末、外部のサービス）。特定の置き場所には固定しない。
- local は複数あってよい。どの local も server・engine・viewer を持ち、編集できる。
- 確定するのは remote である。local の commit は確定ではない。
- online とは、その local がその workspace の remote と push / pull できる状態をいう。online かどうかは workspace ごとに判定する。remote に届くのに拒否される状態は、online とは別の「同期の失敗」として扱う。まだ push していない件数は、online とは別の軸で示す。
- push / pull は当面は手動で行う。挙動を確かめるためである。
- 運ぶ経路は push / pull の一本だけにする。Syncthing はやめる。
- remote の移動は明示の操作で行う。remote が止まっていても、local は commit を続けられる。
- remote を作り直すときは、届くすべての local から、連続していて検証済みの最長の部分を集める。新しい履歴 ID と世代を発行し、古い remote には二度と書かせない。どこまで保全を確認できたかを画面に出す。
- 閲覧専用の端末（iPad など）は clone を持たず、remote に接続して読む。
- branch は持たない。確定の系列は workspace ごとに一つである。
- 確定は remote の journal への fsync で成り立つ。remote の保存媒体を失えば、どの local にもまだ配られていない確定は失われうる。そのときは、復旧した地点と、欠けたかもしれない範囲を示す（複雑さを避けるための暫定。二媒体での保全は当面持たない）。

これにより、物理配置の原則の「確定者（writer）を端末に固定する」「Mac mini を集約点にする」「他の PC は確定者へ Command を送る」を、remote と local の関係に置き換える。

## データの形

- 権威を二つに分ける（DC39）。
  - durability authority（system of record）は journal と snapshot である。replication・backup・PITR の単位はこの二つで、engine には依存しない。
  - semantic authority は各端末の Neo4j である。ドメインモデルを保持し、invariant の検査と query を担う。Neo4j は journal と snapshot から replay で再構築できる。
- journal は確定の記録である。workspace に一本で、remote が全順序を付ける。確定の順番、`commandId`、端末、世代、履歴 ID を持ち、復旧と push / pull に使う。未確定の Command は端末ごとの outbox に置く。
- 1 件の確定は、次の順に workspace ごとに 1 件ずつ処理する：Neo4j の上で検査する → journal に追記して fsync する（ここで確定）→ 同じ内容を transaction で Neo4j に適用する → 応答する。応答は適用の後に返すので、確定の直後に読めば新しい値が返る。
- 兄弟順キーは、parent edge（Neo4j の relationship）の property に置く。
- journal と端末の未確定の Command（outbox）は、当面 jsonl のまま置く。書きかけの行の後始末、scope ごとの pull や重複排除の検索の遅さ、outbox の不具合が繰り返し起きたら、SQLite への切り替えを検討する。

## 権限

- 権限の単位は scope とする。workspace では広すぎる。scope の権限が、人の閲覧範囲だけでなく agent の視界も決める。
- 複製の単位も scope とする。local は、権限のある scope だけを clone する。物理配置の原則の「複製の単位は workspace」を改める。

ここから導かれ、まだ確かめていないこと：

- scope ごとに番号と hash の鎖を持ち、local は scope ごとに pull して照合する。
- 権限の無い scope を指す alias や relation edge は、中身を出さない参照として表示する。
- 二つの scope にまたがる変更には、両方の scope への書き込み権限が要る。scope をまたぐ移動は、当面は実装しない。
- relation edge は、両端が同じ scope にあるときだけ可視化する（暫定。後から変える前提）。
- 権限の変更も journal に記録する。外した後の local には消去を指示するが、すでに渡ったデータは回収できない。

未決：入れ子の scope の権限の規則。全体を非公開にして一部だけを公開する使い方もあるため、祖先の拒否と子の許可のどちらを優先するかは追加で協議する。

## merge の価値観

- node が存在することは、並び順より優先する。並び順を理由に、node の作成を拒否したり競合にしたりしない。別々の端末が作った子どうしの並びは、規則で機械的に決めてよい。
- 挿入とは、足してから並べ替えることである。挿入と並べ替えは別の操作として扱う。
- 並べ替えどうしがぶつかったら、後から確定した方を採る。並べ替えた node が削除済みなら、その並べ替えは消える。
- 同じ兄弟順キーが二つできたら、remote が確定の時に後から来た方のキーを作り直す。人には知らせない。端末がキーを作ってよいという record-schema の DA27 はそのまま保つ。
- merge の方針は、「操作の種類 × 操作の種類」の表として書き切る。各マスには「自動で合わせる」「規則で片方に決める」「競合として人に返す」のどれか一つを入れる。迷うマスはまず人に返し、実際に使ってうるさかったマスから自動にしていく。

- 競合の判定は欄ごとの compare-and-set とする。Command に変更前の値を持たせ、remote で今の値が変更前と一致すれば適用し、変更後と一致すれば実差分なしとし、どちらとも違うときだけ競合にする（途中で値が一周して元に戻っていても通す）。Undo だけは、その Command が作った値がまだ残っている証拠を要求する。
- 削除は、削除する側が見ていた node の集合を基準にする。見ていなかった追加や移動を巻き込むなら、削除全体を競合にする。
- 競合は、関わる scope すべての権限を持つ編集者なら誰でも解ける。解決は独立した Command として記録する。
- root の削除のような危険な操作を防ぐため、node と scope にロックを付ける（Miro の普通のロックに倣う）。ロックは権限の代わりではなく誤操作の防止である。
  - 掛ける・外すのは、その scope を編集できる human である。外すのは確認を挟んだ明示の操作一回で、承認を要しない。掛ける・外すはどちらも記録し、Undo できる。
  - ロックは対象に付き、掛けた人が権限を失っても残る。これで、誰も外せないロックと、承認待ちで止まることを作らない。
  - ロックは掛けた node（出現）だけに効き、消すことと parent edge の変更を止める。祖先の削除で巻き込むことも止める。内容の編集・子の追加・兄弟順・祖先の付け替えは止めない。判定は確定のときの `touched` で行う。
  - AI agent はロックを掛けられる。外せるのは、その scope で human から許可を受けたときだけである。許可は継承せず、許可した human がその scope を編集できなくなると効かなくなる。
  - 特定の人しか外せないロックは作らない。必要になったら scope の権限で扱う。

## 過去の情報の残し方

過去の情報は目的ごとに要る期間が違う（復旧、同期、Undo、由来）。残し方は領域ごとに分ける。

- Flash：ほぼ残さない。
- Rapid：作業のしやすさを優先する。journal は保持期間（時間か件数）の分だけ残し、手放す前に snapshot を作る。remote は local の追いつきを待たない。保持期間より遅れた local は snapshot から clone し直し、未確定の Command は前提条件つきで push し直す。重複排除の記録は保持期間より長く残す。死んだ端末は明示の操作で登録から外す。
- Deep：Git のように積み上げる。版ごとに誰が・いつ・なぜを持つ。私的な情報だけは読めなくする手段を用意する。遅れた local も差分を pull できる。
- Deep も journal の版をすべて残すことはしない。journal の保持は Rapid と同じ仕組み（時間と容量の上限）に従う。transaction time の履歴（いつ何が記録されたか）を残す目的は復旧・Undo・監査で、それは保持期間と snapshot で足りる。as-is と to-be、退職の前と後のような意味のある状態の違いは、版の履歴に頼らず、データとして明示的に置く（別の面にする、有効期間を持たせる、など）。
- Rapid と Deep の違いは保持の方針ではなく構造である。Deep は面が重なり合った全体の graph、Rapid は Deep から射影した一面（木）である。scope ごとに Rapid か Deep かを決めるとは、その scope が射影で作られたかどうかである。
- Rapid から Deep への昇格が、Git の commit に当たる。それまでの細かい編集を意味のある一つの版にまとめ、理由を付けて Deep に積む。その時点の snapshot に名前を付けて残し（Git の tag に当たる）、名前付きの snapshot は保持期間で手放さない。価値のある歴史を残すかどうかは、昇格のときに人か agent が判断する。
- 昇格で、同じ実体を指す node を二つ作らない。Deep にまだ無いものは新しい Deep entity にし、すでに有るものはその Deep entity に entity binding で結ぶ。同じ実体の写しが増える状態は denormalization による不整合の温床である。alias から作ったものは参照先で機械的に分かるが、Flash で取り込んだものや手で作ったものが同じ実体かどうかは、人か AI agent が状況を総合して判断するしかない。この判断が昇格の本質的な費用である。system は候補を示してよいが、規則で自動的に結び付けない。判断は誰がしたかの残る Command として記録し、誤りは entity binding を外す Command で直す。
- 射影には二つの使い方がある。観測用のフィルタ（読むための面。構造は Deep を即時に映す）と、作業の面（組み替えるための面。構造の変更は下書きで、書き戻しで確定する）。どちらで作ったかは射影を作る Command で指定し、面に記録する。
- 値コピーはその時点の値を固定した写真で、新しい ID の実体を作るので、同じ実体の写しを生む。使うのは別のものの雛形と、外への持ち出しに限る。時点の姿を残したいときは、意味のある状態として明示的に置くか、名前付きの snapshot を参照する。参照コピーは窓で、常に今の値を映す。

- 保持の方針は scope に付ける。scope ごとの log の保持期間を、時間と容量の二つの設定可能なパラメータで持つ（Kafka の topic ごとの `retention.ms` と `retention.bytes` に当たる）。どちらかの上限に先に達した分から手放す。既定値は領域ごとに使ってから決める。
- この保持期間は履歴に掛かる。期限を過ぎて手放すのは過去の op と版で、今の状態は残す。node そのものを期限で消す設定は、別の属性として、明示的に有効にした scope にだけ付ける。
- 保持の方針は権限と同じ継承と上書きの規則で解決する。
- 複数の scope に関わる op は、関わる scope のうち最も長い保持期間で残す。
- 重複排除の記録は scope の保持期間に連動させず、workspace 単位で再送が来うる期間より長く持つ。
- archive に移した journal は 90 日で削除する。削除の条件は、その範囲を覆う snapshot の検証が通っていることである。
- 保持期間の短縮は、過去を即座に捨てる破壊的な操作なので、確認つきの明示の操作にする。
- 古すぎる local の判定と clone し直しは scope ごとに行う。

未決：各領域の保持期間の既定値（使ってから決める。Rapid の初期値の目安は 30 日）。scope をまたぐ relation edge の履歴をどの scope に属させるか（推奨：source の scope）。scope ごとの snapshot が参照先の欠けを許すか、scope 間の一貫した切断面を保証するか（推奨：参照先の欠けを許す）。
