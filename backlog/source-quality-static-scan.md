# beta/src ソース品質：静的検査で判明した問題

経緯：fit 修正（e2faa94）のあと、パンとズームの操作感が悪化した件を調べていた。その途中で akaghef から「実装のたびに、それまで OK だったものを壊す」「viewer.ts がデカいとずっと言っているのに改善しない」と指摘があった。描画問題からいったん範囲を広げ、関数単位の規模と複雑度を静的検査で測った。

## 計測方法（再現用）

- 対象：`beta/src`（製品コード）。試験・perf・scripts は別に集計した。`final/` はリリース用の複製なので除外した。
- ツール：ESLint 9 と typescript-eslint 8（作業用ディレクトリに導入し、リポジトリには未導入）。
  - 有効にした規則：`max-lines-per-function`（max 1、空行とコメントを除外）、`complexity`（max 0）、`max-statements`（max 0）、`max-params`（max 0）。
  - 上限を 0 や 1 にしたのは、全関数の値を警告として出力させるため。
- lizard 1.24 も試したが、viewer.ts の構文を追えず `render` などを取りこぼした（249関数しか検出できない）ため不採用。
- 「自前行数」は、入れ子で書かれた関数の行を差し引いた値。CCN は循環的複雑度で、目安は 10超が要注意、20超が高リスク、50超が事実上テスト不能。

## 全体像

- 製品コード：157ファイル、61,493行、関数 3,279個（2行以上のもの）。
- 関数の中央値は 8行、CCN 3。大半は健全で、問題は少数に集中している。
  - 自前行数 100超：24関数。CCN 20超：83関数。CCN 50超：12関数。
- 試験コードは健全（CCN の中央値 1、20超は3関数）。

## 問題

### IS1：viewer.ts（ブラウザ側）の一枚岩化
- 17,202行で、製品コード全体の28%を占める。関数 1,054個（うち最上位 803個）。
- ファイル全体から読み書きできる可変状態：`let` 154個（`const` 250個）。
- 行数の推移：1,892（2026-04）→ 9,579（05）→ 15,529（07）→ 16,650（10-01）→ 17,202（10-16）。減ったことがない。
- 関数名から推定すると、描画、通信・保存、collab、スコープ移動、選択・ドラッグ、カメラ、ファイル取り込み、注釈、物理演算、WebGL、linear panel、表示テンプレートなど、15以上の分野が同居している。
- CCN 20超の関数のうち、22個がこのファイルにある。

### IS2：キー入力の処理が1関数に集中
- `viewer.ts:16306` の `document.addEventListener("keydown", …)`：自前行数 634、**CCN 411**、文の数 478。
- 全ショートカットが1つの分岐の塊に入っている。1つ直すと別のショートカットが壊れる構造（例：61e3568 の修飾キー判定）。
- 受け皿の `viewer_keyboard.ts` は既にあるが、中身は移っていない。

### IS3：描画処理が閉じた入れ子の中にある
- `viewer.ts:7848` の `renderScene`：入れ子込みで 686行、自前行数 188、CCN 46。
  - 中のノード間リンク描画ループ（`viewer.ts:8002`）：178行、CCN 88。
- WebGL のスナップショットは SVG を一度描いてから吸い出して作っており、ここが描画の重さと結合の根っこになっている。
- `applyZoom`、`moveCameraTo`、`render` を fit・パン・ズーム・アニメーションが共有しており、局所的な修正が他の経路に波及する（e2faa94 の事例）。

### IS4：ポインタ入力も巨大
- `viewer.ts:15696` の `canvas.addEventListener("pointerdown", …)`：153行、CCN 64。

### IS5：start_viewer.ts（サーバー側）の一枚岩化
- 4,363行。名前は viewer だが、中身は Node のバックエンドのほぼ全部。素の `http.createServer` の上で、静的ファイル配信と約25系統の API ハンドラを手書きの if で振り分けている。
  - 主な関数：`handleAgentMapApi` 383行・CCN 83、`handleHomeApi` 316行・CCN 89、`handleApi` 212行・CCN 69、サーバー本体の処理（`:4128`）199行・CCN 87、`handleSyncApi` 157行・CCN 49、`handleCollabApi` 149行・CCN 47。
- ルーティングを自作している。既存のルーティングライブラリに置き換えれば、自作部分ごと消せる可能性が高い（方針：自作せず外部ライブラリに頼る）。
- ファイル名が実態と合っていない（「viewer を起動するもの」ではなく「サーバー全体」）。
- 方針（2026-10-16 合意）：数十段の if を順に試す方式をやめ、**木構造で振り分ける**。
  - 木はライブラリに任せ、自作しない。Fastify の find-my-way は基数木、Hono の TrieRouter はトライ木で、URL を1段ずつ辿るため順番による事故がない。
  - コードも木にする。幹（`app.ts`）は URL の先頭で分野ごとのサブルーターに振り分けるだけにする。枝（`routes/<分野>.ts`）は1分野1ファイルで、短い処理の一覧表にする。
  - 手書きの `parse*Route` / `is*Route`（23個）は全廃する。本文の読み取り・形式チェック・エラー応答は、ライブラリの共通の仕組みに寄せる。

### IS6：その他の巨大関数
- `node/blueprint_importer.ts:580` `importBlueprintToAppState`：326行、CCN 85。
- `node/rapid_mvp.ts:405` `copySubtree`：CCN 80。`writeScopedState`：170行。
- `labs/ot/cut/surface-overview/logic.js`：4,758行、CCN 20超が13関数（lab 用の JS）。

### IS7：肥大化を止める仕組みがない
- 行数や複雑度の上限を CI で検査していない。新機能は既存ファイルへの追記が最短経路になる。
- 6月に作った分割 spec 4本（`.kiro/specs/{edge-port-seam,layout-seam-lab,node-draw-seam,progressive-nav-seam}`）は、どのタスクにも完了チェックが付いていない。
  - 一部は共通モジュールとして切り出された（`layout_port.ts`、`node_draw_svg.ts`、`edge_port.ts`）。それでも viewer.ts は減っていない。
- 性能の計測ツール（`beta/perf/run_webgl_pan_zoom.mjs`）はあるが「CI ゲートではない」と明記されている。実行を求める規則もなく、基準値も残っていない（`beta/perf-results/` は空）。
- 合否は機能試験の通過だけで決まり、既存の挙動や操作感を守っているかは判定に入っていない。

## 対策候補（未決定）

- PR1：上記の ESLint 設定を、違反を増やさない CI ゲートにする（現状の違反は基準として許容し、新しい違反だけを不合格にする）。viewer.ts の行数と `let` の数も、増えたら不合格にする。
- PR2：キー入力処理を、コマンドの一覧表と `viewer_keyboard.ts` に移す（IS2）。
- PR3：サーバーの API 振り分けをルーティングライブラリに移し、ファイル名も実態に合わせる（IS5）。
- PR4：カメラ・viewport を1つのモジュールに切り出し、性能の基準値で守る（IS3）。
- PR5：分割 spec 4本の担当・優先順位を決め直し、完了の条件を「viewer.ts の行数が減ったこと」にする（IS7）。
